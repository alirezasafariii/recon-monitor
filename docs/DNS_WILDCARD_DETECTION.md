# Explicit DNS wildcard candidate detection

The DNS stage no longer uses omission from dnsx wildcard-filter output as evidence. It separately queries each eligible discovered host and three independently generated 96-bit random sibling names under the host's immediate parent, in two rounds, for A, AAAA and CNAME. All queried names must match the target include/exclude scope and remain below a configured policy root. Random names are not added to assets or DNS records. Policy roots themselves are not synthetic wildcard host candidates.

A wildcard candidate requires identical, stable positive CNAME answers across the host and every random control in both rounds, or exact stable A/AAAA RRsets across all of them. Address overlap alone is insufficient. A known differing response profile (including CNAME or AAAA) prevents an address-only match from classifying a shared CDN surface. Stable CNAME can support a candidate despite rotating addresses; rotating address-only responses remain unknown. This is evidence of a wildcard response surface, not proof that the named host is nonexistent, or that its HTTP virtual host is identical. Candidates are never removed from DNS, URL or port input.

A previous wildcard flag can be cleared only when all controls explicitly report no A/AAAA/CNAME values in both rounds, while the candidate host has a stable positive answer. No JSON, warnings, tool failure, conflicting rows, resolver errors, malformed values, changing responses and unobserved hosts are unknown. Unknown and unprobed hosts preserve previous flags. Explicit negative evidence must be NOERROR with an empty requested RRset, NODATA, or NXDOMAIN, never silent collector output.

Limits: at most 16 immediate parents and 128 candidate hosts per invocation. Each parent group reserves 6 * (candidate hosts + 3) logical DNS queries before any controls execute. Reservation uses the existing DNS budget and runtime check; insufficient remaining budget prevents probing that group. dnsx receives the existing DNS rate, concurrency cap, process timeout and one DNS attempt per query. Resolver-internal recursive traffic is not a separately counted Recon request. No production timeout increase or Python dependency is added; the explicit-negative fallback optionally uses the system dig binary. Narrow include/exclude rules that do not authorize the random controls cause a scope skip; labels are never tried outside policy to bypass that restriction.

`dns-wildcard-evidence.jsonl` records host, parent, state, reason, generated controls, normalized per-round answers and query outcome metrics. Raw per-type JSON files remain in the current run folder. `wildcard_probe_queries` reports the reserved envelope (which can exceed executed queries after runtime interruption); `wildcard_unknown_hosts` counts unknown classifications. `wildcard-candidates.txt` contains newly observed candidates, not historical flags. Wildcard enrichment coverage is independent of primary DNS collection. Incomplete classification is recorded by wildcard_classification_complete, wildcard_unknown_hosts and wildcard_coverage_reasons; it does not make an otherwise complete DNS collection partial or block its baseline. Missing or failed primary DNS observations still make collection partial. Preserved resolved hosts still feed downstream. A DNS stage using only the system resolver cannot establish new wildcard classification.

The feature is intentionally bounded: variable wildcard responses without a stable comparable CNAME, unsupported dnsx JSON contracts, and groups beyond limits remain unknown. Audit files are local run artifacts and follow ordinary retention. There is no automatic repair of historical wildcard flags.

Producer flags: https://github.com/projectdiscovery/dnsx (JSON, rcode filtering, retry and rate options). Offline tests cover both positive and negative controls, CDN variation, conflicting observations, scope, budget, runtime interruption, and the original 100-host warning-only preservation scenario. No live target test has been run for this change.

## Explicit negative fallback

Some dnsx 1.2.3 invocations omit NXDOMAIN and empty requested RRsets from JSON despite rcode filtering. For wildcard enrichment only, clean dnsx omissions are retried with optional `dig`. Both control collectors use the explicit resolver 8.8.8.8; this does not change primary DNS collection. Apple dig 9.10 rejects `-r`. In 8.8.12 the fallback omits that option and checks that `~/.digrc` is absent. The subsequent hardening removes `HOME` only from the dig child environment, so dig cannot read user `.digrc` configuration even if that file appears between preparation and execution. The parent environment and user files remain unchanged. This also permits fallback when a user `.digrc` exists. One attempt, two-second DNS timeout, no automatic TCP retry, and a process deadline of at most five seconds bound each fallback. Production timeout configuration is unchanged.

Only complete responses with the matching question, resolver, non-truncated QR flags and consistent record counts are accepted. NXDOMAIN or empty NOERROR requires an authority SOA for the question or terminal CNAME zone. Failure, malformed/conflicting dnsx rows, warnings, timeout and missing dig preserve unknown. Fallback never updates DNS records or adds control assets.

Each fallback attempt consumes one additional DNS budget unit, respects scope, runtime/operator interruption and DNS rate, and has a shared cap of 128 attempts per detector invocation. Cap/budget exhaustion remains optional wildcard coverage loss, never primary DNS failure. Raw dig replies, resolver, query, exit status and normalized observations are recorded in dns_wildcard_outcomes and per-query artifacts.

Configuration isolation follows the BIND 9.10.6 implementation: `bin/dig/dig.c` reads `.digrc` only inside the `getenv("HOME") != NULL` branch. Source: https://github.com/isc-projects/bind9/blob/v9.10.6/bin/dig/dig.c
